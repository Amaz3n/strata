# Reservation conversion — source safeguards implemented, atomic completion unfinished

The original `convertHoldToReservation` owner now validates the hold and embedded lot before any write. It rejects expired holds, malformed or foreign parent evidence, unsellable lots, missing community/buyers, mismatched lot/community divisions, inaccessible linked homes, an existing home buyer or purchase agreement, and an earlier earnest invoice. Source query failures remain failures. Existing project/invoice services remain the writers; no second financial implementation was introduced.

Home assignment and new-home lot linking now inspect returned errors/rows and bind the source version. New lot linking requires an unlinked lot. Failed link or home assignment stops before a new deposit. The final reservation update requires the original hold/version, current expiry, and no deposit/agreement link. A lost or failed completion is reported for inspection rather than recording a false reserved event. These checks reduce unsafe sequential retries and silent overwrites; they are not a database claim or transaction.

The form preserves fractional dollars from existing integer cents, uses the shared decimal-string money parser, rejects blank/negative/malformed amounts, and disables edits while submitting. Form and service share the verified invoice integer limit of 2,147,483,647 cents. Production catalog metadata confirms `invoices.total_cents` and `invoice_lines.unit_price_cents` are `integer`; unsupported amounts now reject before a home or lot write. Success says invoice created, since queued delivery does not prove provider acceptance.

The isolated source/service and actual Supabase SDK/custom-fetch tests exercise denied/moved/foreign/expired references, failed reads/writes, original owners, exact cents, current home/hold/version filters and absent completion replies. The fake update fixture initially did not implement `.maybeSingle()` cardinality for updates: it returned arrays, including an empty array. Correcting that fixture exposed the intended rejection; the actual SDK transport case separately verifies null completion. Tests do not prove real JWT/RLS, independent sessions or full-schema transactions.

**Atomic conversion remains unfinished.** A preserved counterexample changes a hold after invoice creation: the conditional reservation update rejects and records no reserved event, but one invoice already exists. This remains an unacceptable national-builder transaction gap. Initial inspection for a previous invoice cannot stop two concurrent workers from creating one each. Failed new-home lot linking can also leave an orphan home. No accepted task or release gate is claimed.

The original project and invoice writers now use shared, write-free preparation functions. Project preparation includes its normalized row, billing contract terms, financial settings with inherited cost coding, and accounting dimensions. Invoice preparation includes original line/retainage/discount calculation, header metadata and the issued snapshot. The normal writers call these functions; they are not an alternate writer or an unused proposed calculation. Issued snapshot and header now share the same supplied issuance timestamp. Synthetic tests call the normal project/invoice owners as well as preparation, covering mixed-org posture, unpriced production billing, preserved approved changes/fees, inherited versus explicit cost coding, dimension edits, exact deposit cents and approval/token checks. No preparation function authorizes or writes by itself.

Shared preparation is an implemented prerequisite, not atomic reservation completion. The existing conversion still calls the owners separately and the preserved post-invoice hold-change counterexample remains. Next work must integrate these preparations with the reservation transaction and original reviewed UI request/recovery; a prepared row alone cannot be accepted as a completed national-builder workflow. Preparation evidence records this change separately from the earlier guards.

The next implementation must register and persist the original actor/org/request identity and exact reviewed UI body/source versions; lock/re-authorize the actual community/lot/hold/buyers/home; reuse the shared original project and invoice preparation; atomically commit home/hierarchy/financial setup/lot/reservation/deposit ownership and immutable receipt/event/audit; and reserve provider delivery before sending. Replaying the original request must inspect the same result, while changed body or parent facts reject without another home/invoice. Recovery must remain available after lost replies, reload, cancellation and current-role changes. Legacy/direct writers and invoice issuance ambiguity also need reconciliation.

Source tracing confirmed `createProject` normalizes retainage into its input, which invokes billing-contract/financial-setting setup even when conversion supplies no explicit billing fields. It also saves default accounting dimensions. An atomic conversion cannot substitute a minimal raw project insert and omit those behaviors. `createInvoice` owns posture, issued snapshot, invoice-line calculation, bookkeeping and durable issuance routing; its invoice/line transaction alone does not include the other conversion records. Preserve those owners and their defaults in the shared preparation/commit integration.
